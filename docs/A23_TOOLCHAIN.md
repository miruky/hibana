# A23 ステージ生産ツールチェーン

制定日: 2026-07-27

31 ステージの Blender 外装を、面ごとの職人作業ではなく共通の測定付きパイプラインで作るための道具立て。`tools/blender/a23/` に置き、`tools/blender/a23_bridge.py` 経由で `build_all_stages.py` の汎用経路へ接続する。中庭 (nakaniwa) は専用キットを持つため `tools/blender/stage_kits/nakaniwa_a23_reconciliation.py` から同じ処理を受ける。

## モジュール

| モジュール | 役割 |
| --- | --- |
| `a23/kit.py` | `SpecKit` / `RenderKit` アダプタ。各モジュールは特定ステージのキットを import せず、`SpecKit.from_module(任意のキット)` を受け取る |
| `a23/reclamation.py` | 三角形の再配分 4 パス。カメラ集合と対象グループは引数 |
| `a23/districts.py` | 区画の走査線配置、分節化、契約由来の窓律動、遮蔽考慮の優先度 |
| `a23/materials.py` | 材質ファミリの分割と床/壁の分離。任意のキットの `MATERIALS` と地面ロールに対する変換として表現 |
| `a23/measure.py` | 建築フットプリント、遮蔽考慮のヒーロー画面占有率、厳格な葉判定、カメラ別指標表 |
| `a23/evidence.py` | 多カメラのレンダー harness。ステージ自身の `PROOF_CAMERAS` で駆動 |

### 再配分パスの性質

- **pass 1 / pass 2** — 見えないものを削る最適化
- **pass 3** — **最適化ではなく正しさの修正**。5 カメラすべてで隠れていることを要求する。pass 1/2 が 1 カメラ基準で判定していたため、別カメラから 52〜120m の距離で明瞭に見える建物を丸ごと削除していた。**鎖から外してはならない**
- **pass 4** — その場での簡略化。面取り幅が全カメラで sub-pixel な `chamfer_box` を `box` へ落とすなど。シルエットは構造上変わらない

## 計測の欠陥 4 件（再発させないための記録）

このラウンドで実際に代償を払ったもの。31 面規模では被害も 31 倍になる。

### 1. 単一カメラ判定

16 イテレーションにわたり dual-hero カメラ 1 枚だけで良否を判定し、マップの 65% が空き地であることを検出できなかった。再配分の 2 パスも同じ理由で、1 カメラから見えないが他 2 カメラからは明白な建物を削除していた（PalaceWaterCourt で 5.84% / 31,293px の欠損）。

**対策**: 判定は必ず複数カメラで行う。`a23/evidence.py` はそのために存在する。

### 2. 指標のインフレ

HSV の緩い葉判定が、影の落ちた石材を葉として数えていた。ある場面では「25,226 画素」に対し真値は **0**。

**対策**: 葉の計測は緑優勢（`g > r + 12` かつ `g > b + 12`）を必須とする。`a23/measure.py` の `foliage_mask_strict`。

### 3. 集計での失敗

個別には安全な変更が、同一フレームに多数集まると閾値を超える。面取り削減を 1.5px 閾値で適用したとき、最大の連結成分は 235px に過ぎないのに、多数の建物の微小な稜線ハイライトが累積して 1 カメラが 0.596% に達した（0.6px へ締めて解決）。分節化を全 18 棟へ広げたときも、コーニスの張り出しが路地の両側に付いて最悪幅が 4.5m 対契約 5.0m になった。

**対策**: 個別の安全性ではなくフレーム全体・最悪ペアの数値を見る。

### 4. 変化検出の盲点

差分ベースの計測は、対照と候補の**両方に等しく存在する欠陥を原理的に検出できない**。親サーフェスを持たず空中に浮く 4×8m の発光カードが、20 イテレーション生き延びた。

**対策**: 対照を参照しない絶対的なフレーム検査を併用する。発光プロップは親と接触を必須とするビルド時アサーションで守る。

## 検証の原則

- **データ変更は、それを読む検証器では検証できない。それを消費するコードでしか検証できない。** レイアウトへランドマーク配置をマージした際、契約検証もテストスイートも全て緑だったが、生成器から見れば 21 面分が即クラッシュするデータだった。
- **受け入れ試験は観測可能な成果物で定義する。** スペックが byte-for-byte 一致していてもレンダーが 10〜35% 乖離した実例がある（暗黙の `deepcopy` 連鎖が材質上書きを運んでいた）。中間データの一致を合格としない。
- **技術 PASS を視覚 PASS と呼ばない。** 予算・監査・検証器がすべて緑でも、独立レビューは別のゲートである。

## ハッシュの自己参照について

`stage-layouts.json` の `placementSolverSha256` は、かつてファイル自身の生テキストをハッシュした値を自分の中に格納していたため、不動点が存在しなかった。`stage-placement-solver.mjs` の `normalizedLayoutsPayload()` が当該フィールドを除外してからハッシュする。`codegen-stage-world.mjs` の `normalizedCatalogPayload` が `catalogSha256` に対して既に行っていた処理と同じ規約。

**この不整合はランタイムだけが検出した。** オフライン検証はどれも見ていなかった。provenance の厳格さは、古い資産の出荷を実際に防いでいる。
